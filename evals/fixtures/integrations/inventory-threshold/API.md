# Inventory and warning service contract

These are fictional services for local HTTP mocks. The operations team maintains inventory access across customer instances; the integration receives its resolved inventory base URL and bearer token from that managed connection. Customers do not enter or copy the inventory token. Each customer configures a warning-service base URL and bearer token, a warehouse ID, a nonnegative integer threshold, and a check cadence. The fixture does not provision any platform connection. No live endpoint or credentials are provided.

`GET /warehouses/{warehouseId}/stock` accepts optional `cursor` and returns `200 { "items": [{ "sku": "part/A", "available": 2, "updatedAt": "2026-09-01T10:00:00Z" }], "nextCursor": "opaque-next" }`. The final page has `nextCursor: null`. Each check's pages form a complete warehouse snapshot with each SKU once; cursors are opaque and URL parameters and warehouse IDs must be encoded. `available` is a nonnegative integer. A product may be low on the first check, remain low over many checks, restock, and fall low again. An unchanged product retains its `updatedAt`; a stock change gives it a new one. Source errors return non-2xx.

`POST /alerts` accepts JSON `{ "warehouseId": "west", "sku": "part/A", "available": 2, "threshold": 5, "observedAt": "2026-09-01T10:00:00Z" }` with a bearer token and an `Idempotency-Key` header. `observedAt` is the source item's `updatedAt`, not the time the scheduled check ran. Return `201` on acceptance. Repeating the same key and body returns the same acceptance; reusing a key with a different body returns `409`. Any stable key for one warning is valid, including a stored generated key; a later healthy-to-low transition must use a distinct key. The service can return `503`; that warning has not been accepted. No other endpoint or implicit retry guarantee exists.

For this integration, `available < threshold` means low. The first observed low snapshot deserves an alert. A later healthy observation makes a subsequent low transition alertable again. A failed alert must remain eligible on a later check. A successful earlier alert may be replayed through the idempotent endpoint during recovery.
