# Office onboarding reminders

People Operations owns this little job. An old Linux scheduler runs it every fifteen minutes in UTC. At each office's local 8am hour on weekdays, it sends that office's coordinator the list of staff starting on the next weekday. On Friday it prepares Monday's starters. We do not currently account for public holidays. Each coordinator sees their own office's list, not a consolidated global message. HR maintains offices.json; it is account-specific configuration, including timezones and coordinator addresses.

The gateways are internal services. Their interfaces are available from the service team:

- Planning GET /v2/offices/{encoded office ID}/onboarding?start=YYYY-MM-DD with its bearer credential. Returns {people:[{id,name,team,cancelled,notifyManager}]}. IDs and fields are strings except the two booleans. Records belong to the requested office and start date; there are no more pages. HR freezes the next-day notification packet at the beginning of the office's 8am window, so repeat calls during the window return identical records even if array ordering differs. Staff IDs are unique within a packet. Blank name or team strings are legal and are passed through as entered by HR. Cancelled starters and people whose manager notification is turned off should not appear.
- Mail POST /v1/messages with a different bearer credential, JSON {to,subject,text}, and Idempotency-Key. A successful 202 means the service has durably accepted the message for delivery. Repeating an identical body under the same key for seven days returns 202 without sending a second message; a changed body under that key returns 409. The service compares object values, not JSON whitespace/key order. Keys are shared across all callers of the same service account. This is why replacing our job must preserve its keys during handover. Failure responses are not successful acceptance. A network timeout can happen after acceptance.

No email credentials or gateway tokens are included. A deployer can supply those service connections. Both gateways can return 429 or 5xx; the script does not retry within a run and exits on the first error. Earlier accepted messages remain accepted. The next scheduled run within the 8am hour tries again; once that hour ends, operations investigate missed notifications manually. There is no automatic catch-up after the window. Hosts have system timezone data; the Python zoneinfo library applies daylight-saving changes.

We want to retire the Linux job without moving everyone's reminder to one UTC hour, combining offices, duplicating emails during handover, or silently adding weekend/public-holiday rules. Existing production email sending must remain off during local development. Coordinator and office settings should remain manageable without source edits.
