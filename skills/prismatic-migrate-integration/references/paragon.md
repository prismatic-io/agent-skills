# Paragon source semantics

Use this for Paragon Workflow or Paragraph sources. A Paragraph project is useful executable-definition evidence, not a complete export of deployed customer state. These notes do not define a fictional universal workflow JSON format.

## Obtaining and reading a project

The official `@useparagon/cli` provides `para`; after account authentication, `para init --create-from-existing` selects an existing project to export. Paragraph represents integrations, Connect Portal configuration, and workflows. Export access depends on the available account and permissions; the export guide does not establish universal plan entitlement. [Paragraph getting started](https://docs.useparagon.com/paragraph/getting-started).

The documented layout is `src/integrations/<integration>/`, containing `workflows/`, `config.ts`, and `inputs.ts`. Workflow definitions use TypeScript/JavaScript with Paragon steps, output references, branches, and registered orchestration. Imported modules and installed package versions therefore matter; this is not ordinary JavaScript whose statements alone describe runtime execution. App Events live in `src/events`; their names and payload definitions are part of the application-facing trigger contract. [Integration structure](https://docs.useparagon.com/paragraph/defining-integrations), [workflow definitions](https://docs.useparagon.com/paragraph/defining-workflows), [App Events](https://docs.useparagon.com/paragraph/defining-app-events).

`para build` compiles and evaluates the project into `out/build.json`. Build success validates source structure, not migrated behavior. Exported dashboard Function code can fail TypeScript checks because it was originally untyped. Preserve the distinction between an incomplete source, an export typing problem, and an incorrect port. The documented build artifact is not a promised stable interchange schema. `para pull` can overwrite local edits and remove definitions missing upstream; `para push` changes the remote project. Project/build identifiers are not a supported mechanism for copying projects. [Build, pull, and push](https://docs.useparagon.com/paragraph/build-and-push).

## Configuration and customer scope

Paragraph excludes environment secret values, signing keys, OAuth client credentials, built-in integration OAuth scopes, and organization team roles. Custom-integration scopes are included in their configuration. A source checkout cannot demonstrate that these missing values, customer grants, or secrets have been migrated. [Export exclusions](https://docs.useparagon.com/paragraph/getting-started).

`inputs.ts` defines customer-facing user settings and mappings. Setting IDs are stable identifiers: changing them can discard existing customer selections. Custom-integration configuration can also contain authentication protocol, API and token endpoints, scopes, and authorization construction. Read these alongside workflows that depend on settings or connected-user identity. Definitions of settings are not evidence of each customer's selected values. [User settings and custom integrations](https://docs.useparagon.com/paragraph/defining-integrations).

Release environments are separate projects with distinct IDs, signing keys, secrets, and connected users. A development export is not proof of production configuration. Releases can enable default-enabled workflows or create new triggers for connected users, so deployment can have effects before the next ordinary workflow call. [Release environments](https://docs.useparagon.com/deploying-integrations/release-environments).

## Runtime behavior beyond the graph

- **Request triggers and responses:** invocation uses an authenticated Paragon user; configured input validation can reject a request before workflow actions. Without a custom response, the caller receives an immediate HTTP 202. A Response step defines the HTTP status separately from the response body's key-value mappings to earlier outputs. Current documentation gives the workflow 55 seconds to reach that step; HTTP 542 indicates a response timeout and can arrive while the workflow continues. Its execution ID supports follow-up through monitoring or task history. [Request Trigger](https://docs.useparagon.com/workflows/triggers/request-trigger).
- **Fan Out:** iterations run in parallel; downstream steps wait for all iterations. Do not infer sequential ordering; preserve the join and any behavior that depends on concurrency. [Fan Out](https://docs.useparagon.com/workflows/using-fan-out).
- **Auto Retry:** when enabled, retries apply to the failed step, not the entire workflow. Test Step and Test Workflow do not exercise retries. The documentation's attempt-count wording and retry schedule are not perfectly aligned; establish exact deployed behavior if counts or timing affect correctness instead of hardcoding an inferred policy. [Auto Retries](https://docs.useparagon.com/workflows/auto-retries).
- **Smart Rate Limits:** supported integrations automatically pause workflows and resume by retrying the suspended/failed request. This can exist without a visible retry node; support includes action-specific exceptions. [Smart Rate Limits](https://docs.useparagon.com/workflows/handling-rate-limits).

Local mocks can establish transformations and branch behavior without establishing hosted orchestration, connection ownership, or delivery recovery. Historical workflow evidence is available through the dashboard and, where entitled, the Enterprise Task History API. Missing API access is not evidence that historical behavior is absent. [Task History API](https://docs.useparagon.com/apis/task-history). Use the [official documentation index](https://docs.useparagon.com/llms.txt) to locate the actual trigger/action product and version; Paragraph Workflow knowledge should not be assumed to cover ActionKit or Managed Sync contracts.
